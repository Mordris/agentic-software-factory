## Two-mission demonstration

1. Initialize a fresh owned ledger and two synthetic repositories. Print the actual toolchain/SQLite identities and hashes of schemas, plans and fixture inputs.
2. Use the trusted operator path to approve both exact fixture plans. Verify a negative unapproved control cannot dispatch.
3. Start both missions and demonstrate compatible overlap plus a serialized conflicting allocation. Record reservations, attempts, messages and their causal IDs.
4. Let A's independent fixture evaluator detect the deliberately wrong result and issue a bounded rework request. A worker's self-reported success must not override that failed gate.
5. Request cancellation of B while its fake attempt is active. Observe the request separately from acknowledgment; keep A progressing.
6. Kill the owned coordinator at a recorded transaction/outbox boundary. Restart from the same ledger, reconcile attempts and verify that capacity/evidence has not been consumed twice.
7. Submit late B events and duplicated A outcomes. Confirm rejection/deduplication. Complete A's corrected fixture and independent check.
8. Inspect A's exact synthetic delivery preview and stop at `awaiting_action_approval`. Confirm B is terminally canceled and the replayed projection matches. No push, PR, message, deployment or real repository mutation occurs.

## Test design and evidence receipt

Use deterministic clocks and scheduler choices for ordinary transition tests; bounded real processes for restart/termination cases. Property tests use independently described model invariants and hostile command/event sequences. Start with 100 generated runs per property and at most 200 commands per run, within the brief's runtime envelope. Record seed and shrunk counterexample; add a focused regression for each concrete failure before increasing the run budget.

Test assertions must distinguish plausible defects: for example, a mutation that removes the plan hash comparison, fencing check, mission predicate, receipt digest check, transaction coupling, or failed-QA gate must make its associated test fail. Use bounded deliberate controls for these critical paths; passing line coverage alone is insufficient. Do not add a full mutation-testing platform to this milestone.

Each row's evidence record contains requirement ID, source snapshot and patch/input digests, case name, exact argv/cwd, toolchain/lockfile/native build identity, exit/signal, timestamps, observed resource limits, artifact hashes, classification and coverage limits. Keep all required rows visible, including blocked/unexecuted rows. The evidence index distinguishes actual process/database behavior, injected faults, and reviewed reports.

Coverage reports explain unexercised critical paths. All authority, reservation, gate and recovery requirements need positive and adverse controls; an arbitrary repository-wide percentage cannot waive one. Tests are limited to observable requirements and significant failure paths.

## Completion boundaries

Local completion requires P1-01 through P1-21 with reproducible evidence and an accurate limitations report. P1-21 is a manual local qualification, outside credential-free hosted CI, and is valid only for its recorded probe/runtime/model/settings inputs. In particular, a latest-version compatibility blocker is not a passing version policy, and a scanner that sees zero packages is not a clean dependency review.

Hosted CI success, hosted image compatibility, and any new required-check/ruleset configuration remain unverified until the exact source is separately approved for publication and the resulting runs/settings are read back. Phase 1 completion does not qualify remote transport, browser behavior, live models, real process isolation, multi-user authority, or real OSS delivery.
